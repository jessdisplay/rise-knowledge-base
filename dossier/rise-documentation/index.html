How the mapping works — and the NDIA APIs

Part A documents how Rise's mapping actually works, with every technical idea linked to its plain-language home in the training ladder. Part B gives the developer a verified starting map of the NDIA API landscape. Written 8 July 2026.

Every claim on this page carries a tier: V verified against a primary or official source this session (URLs in §Sources) · C corroborated by a credible secondary source, dated where it matters · T tentative — supplied by the briefing or general knowledge, not verified; confirm with the DPO before relying on it · D design choice or strategy — Rise's own call, not a fact.

Part A — the mapping, explained

A1 · One graph, many surfaces D

There is exactly one dataset: a graph of nodes (a rule, a policy, a register row — each is a dot) and typed edges (labelled arrows saying why two dots connect). Everything a user ever sees — the nine steps, the coverage map, the navigator, the gap report — is a rendering of that one graph at a chosen zoom. No surface holds its own copy of the truth in production; the current HTML prototypes embed data copies and say so on their faces.

A2 · Addresses are the join keys V

Every standard carries a dual statutory address — its clause in the Rules 2018 and its indicator section in the Quality Indicators Guidelines — and the pairing is legislated by eleven tables inside the Guidelines themselves, read directly from the instruments. Rise's cell IDs are human handles over those addresses: CORE-2.3 means core module, governance part, third standard — which resolves to Sch 1 cl 11 ↔ s 13 (Quality management). The address, not the name, is what joins layers together, because names drift (eight standards are titled differently in the two instruments) and addresses don't.

A4 · Who said so D — verified against NIST OLIR practice

Every edge records three separate things: its semantic type (the label above), its assertion source (a human made it · it was read straight from the law · a machine suggested it), and its verification status. Machine suggestions are born needs_review and stay that way until a person confirms them. Type is never confidence; trust is recorded, not assumed.

A5 · Time V — the legal hook is s 24

Nothing is deleted. A change creates a new node or edge that SUPERSEDES the old one, so the graph can answer "how did things stand on 30 June last year?" — the auditor's favourite question. The legal reason this is day-one architecture, not polish: the Rules apply the quality indicators "as existing from time to time", meaning the current compilation always governs, and this framework amended twice in 2026 alone.

A6 · Does it apply here? V — the gate is legislated

Applicability is not opinion: the Rules' section 20(3) is a 36-row table mapping every class of supports to its schedules and audit type. Rise ingests it as data, joins it to a provider profile, and prunes the whole experience to what applies — the learner's Level 2 and the gap engine's first gate are the same query.

A7 · Gaps are missing arrows D — model; states testable

Run per indicator, per provider, in strict order: not applicable (gate says no) → unknown (profile too incomplete to evaluate — always reported, never hidden) → documentation gap (no verified IMPLEMENTS arrives) → proof gap (no recent EVIDENCES arrives) → covered, for now. Green means nothing is missing; it never means the work is good — quality is judged by humans.

Part B — the NDIA API landscape, for the developer

B1 · What the program is V

The NDIA runs a Digital Partnership Program (DPP) managing controlled, secure access to some NDIA data and systems via APIs, built for registered providers, plan managers and software developers so they can build tools that improve how participants, providers and the NDIA connect. Approval is based on the type of entity requesting access and its cyber security maturity, and applying does not guarantee access.

B2 · The application path V — from the NDIA's own page

  1. Email the Digital Partnership Office first: dpo@ndis.gov.au. The NDIA's explicit instruction: do not fill out any documents or start the cyber assessment before contacting them — it causes delays.
  2. Download and complete the Digital Provider questionnaire (the briefing's name for this was correct).
  3. Send all completed documents to the DPO (Digital Partnership Office, GPO Box 700, Canberra ACT 2601). A company extract confirms signing authorities on the terms and conditions; alternative signing authority needs evidence; an NDA can be requested for data release.
  4. Work through the architectural review and cyber clearance with the DPO.
  5. If approved: a technical pack including the PRODA B2B software developers guide → register a PRODA test account → activate the vendor developer portal → read the API specifications there (they are not public).
  6. Production: finish the software, then email the API support team to arrange testing.

B3 · The correction that changes Rise's strategy V

Software developers and aggregators must partner with a registered provider to access the NDIA APIs, and face additional cyber security activities. There is also an indirect integration path where a registered provider connects through an aggregator who is already a digital partner. D Strategic consequence the briefing missed: Rise's pilot provider is not just a design partner — the pilot partnership is the application vehicle. "Apply as a platform" remains good positioning language, but the verified rule requires the provider partnership regardless of positioning.

B4 · The API catalogue, honestly dated

C — sector reporting, 2021 APIs released by 2021: payment requests, service bookings, quotations, notifications, products, file uploads, reference data, and the NDIS plan budget — broadly the myplace provider portal's functions, automatable. V The current full catalogue is only visible inside the partner portal after approval. T — confirm with the DPO The briefing's remaining items are not verified: a participant-lookup API, a provider-registration-information API, and PACE-partner interactions. V One reframe: "provider authentication" is not an API you request — authentication is PRODA, the mechanism the technical pack documents. C Scope guardrail from sector reporting: partners access only data a provider would normally see in its own portal, and NDIS Commission registration is expected.

B5 · Security posture expectations

V Assessment weighs entity type and cyber security maturity, and developers/aggregators carry additional cyber activities. C — 2021 reporting The NDIA may enforce recognised standards before onboarding — ISO 27001, SOC 2, and IRAP were named. T Penetration testing "depending on the integration" comes from the briefing only. D Practical read: start Rise's own security paper trail now — and note the symmetry: say it, do it, prove it is exactly what a cyber assessor wants from Rise too. The gap engine pointed at Rise's own ISMS would be a compelling exhibit.

B7 · Hard words V unless marked

DPO — the NDIA's Digital Partnership Office: the team you email first, and the gatekeeper of the whole process (dpo@ndis.gov.au).
PRODA — Provider Digital Access: the Australian Government credential system organisations use to prove who they are to NDIA systems. The technical pack includes its B2B developers guide.
myplace — the NDIA's provider portal. The first APIs mirror what providers already do there.
PACE T — the NDIA's newer internal system replacing its legacy platform. What partners can touch, if anything, is unverified — ask the DPO.
myID T — general knowledge — the individual credential (formerly myGovID), distinct from PRODA's organisation focus. Relevant later if individuals authenticate.

B8 · Developer's next actions

  1. Email dpo@ndis.gov.au — before any paperwork, before any assessment (their instruction, not ours). Introduce Rise as a compliance-and-training platform partnering with a named registered provider (the pilot).
  2. Ask three questions that convert this page's T tier into V or dead: the current API catalogue; whether any participant-scope or provider-registration API exists for our use case; whether any PACE-facing capability is available to partners.
  3. Request the Digital Provider questionnaire and the current terms — and only then start filling anything in.
  4. Begin the security paper trail in parallel: asset register, access control, secure-development practice notes — the artefacts a cyber maturity review will ask for.
  5. On approval, read the PRODA B2B guide first; everything authenticates through it.
